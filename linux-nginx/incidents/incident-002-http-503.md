# Incident 002 — HTTP 503 Configuration Issue

## Incident Summary

Nginx was running, but the website returned HTTP 503 Service Temporarily Unavailable.

## Environment

- OS: Ubuntu 26.04 LTS
- Web Server: Nginx 1.28.3
- Environment: VirtualBox Home Lab
- HTTP Port: 80

## Reported Symptom

The Nginx service was running, but HTTP requests returned:

```text
HTTP/1.1 503 Service Temporarily Unavailable

Investigation
1. Checked Nginx Service Status
systemctl status nginx --no-pager

Nginx was active and running.

2. Tested HTTP Response
curl -I http://localhost

Result:

HTTP/1.1 503 Service Temporarily Unavailable

This confirmed that the service was running but the HTTP request was receiving a 503 response.

3. Validated Nginx Configuration
sudo nginx -t

An initial configuration error was identified because the return 503 directive was missing a semicolon.

The configuration was corrected and the syntax test completed successfully.

4. Inspected Active Configuration
sudo nginx -T 2>&1 | grep -n -C 3 "return 503"

The active configuration contained:

return 503;

This confirmed that the 503 response was being generated by the Nginx configuration.

5. Checked Nginx Logs
sudo tail -n 50 /var/log/nginx/error.log
sudo tail -n 20 /var/log/nginx/access.log

The access log showed requests receiving HTTP 503 responses.

Root Cause

An intentional return 503; directive in the active Nginx server configuration was generating the HTTP 503 response.

Resolution

The test return 503; directive was removed from the Nginx configuration.

The configuration was then validated:

sudo nginx -t

The configuration test completed successfully.

Validation

Tested the HTTP endpoint again:

curl -I http://localhost

Result:

HTTP/1.1 200 OK

The website was responding normally again.

Troubleshooting Approach

HTTP 503 Reported
        ↓
Check Service Status
        ↓
Test HTTP Response
        ↓
Validate Configuration
        ↓
Inspect Active Configuration
        ↓
Check Logs
        ↓
Identify Configuration Issue
        ↓
Remove Test Configuration
        ↓
Validate HTTP 200

Key Learning

A service can be running and listening on its port while still returning an HTTP error.

Therefore, checking only:

systemctl → service status

is not enough.

Application Support troubleshooting should validate multiple layers:
Service
   ↓
Port
   ↓
HTTP Response
   ↓
Configuration
   ↓
Logs
